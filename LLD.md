# Low-Level Design: Live Football World Cup Scoreboard

## 1. Scope

This document describes the design for a small, thread-safe Java library that manages live football matches.

The functional requirements come from the supplied coding-task PDF. The project-specific implementation constraints come from `requirements.md`.

Required operations:

1. Start a match.
2. Replace the score of an active match.
3. Finish a match.
4. Return a summary of active matches.
5. Provide exactly one additional operation: `getMatch(matchId)`.

The library has no REST API, database, framework, messaging, or application-specific infrastructure.

## 2. Decisions and assumptions

- Match IDs are unique `long` values generated by one `AtomicLong`.
- The generated ID also provides the monotonic start-order value. IDs are assigned when matches start, so larger IDs represent more recently started matches.
- A match stores its start timestamp for domain information and diagnostics. Timestamp values do not determine summary ordering.
- `updateScore` replaces both scores; it does not increment them.
- Both scores must be non-negative integers.
- A team name is trimmed before validation and storage.
- Stored team names have their first character capitalized. The remainder is preserved. For example, `" spain "` is stored as `"Spain"`.
- Active-team uniqueness is case-insensitive using `Locale.ROOT`. Thus, `Spain`, `spain`, and ` SPAIN ` cannot represent different active teams.
- A team may participate in only one active match at a time. Teams may participate in another match after their previous match has finished.
- Updating or finishing a finished match is invalid.
- A finished match remains retrievable only while it is present in the bounded history.
- The history retains at most 20 finished matches and evicts the oldest retained entry when necessary.
- Publicly returned match objects are immutable snapshots. A client cannot observe later score changes through an object it already received.
- A summary is assembled from per-match snapshots. Under concurrent updates, different entries may reflect different instants, but each returned match is internally consistent.

## 4. Domain model

### `Match`

`Match` is an immutable value object containing:

```text
long matchId
String homeTeam
String awayTeam
int homeScore
int awayScore
Instant startedAt
long startOrder
boolean finished
```

The public model uses a single immutable representation for both active and finished matches. A finished match is represented by `finished = true`; its final score is the last accepted score.

Construction validates identity-independent invariants:

- team names are non-null and non-blank after trimming;
- home and away teams are different under case-insensitive comparison;
- scores are non-negative;
- the start timestamp is present;
- the start order is positive.

`Match` exposes accessors only. No mutator is provided. Score updates create a new `Match` instance, and finishing creates another instance with `finished = true`.

## 5. Public service API

```java
public final class ScoreboardService {
  public ScoreboardService(MatchRepository matchRepository);

  public Match startMatch(String homeTeam, String awayTeam);

  public Match updateScore(long matchId, int homeScore, int awayScore);

  public Match finishMatch(long matchId);

  public List<Match> getSummary();

  public Match getMatch(long matchId);
}
```

The service validates inputs that are part of the scoreboard behavior and delegates storage concerns to `MatchRepository`. It does not depend on `InMemoryMatchRepository`.

`getSummary()` sorts active matches by:

1. total score descending;
2. start order descending for ties.

The returned list is a new list and is unmodifiable or defensively copied before returning.

## 6. Persistence abstraction

The repository is deliberately small:

```java
public interface MatchRepository {
  Match create(String homeTeam, String awayTeam, Instant startedAt, long startOrder);

  Match updateScore(long matchId, int homeScore, int awayScore);

  Match finish(long matchId);

  Optional<Match> findActive(long matchId);

  Optional<Match> findAny(long matchId);

  List<Match> findActiveMatches();
}
```

The repository owns active-match storage, finished-match history, atomic state transitions, and repository-specific synchronization. The service owns the scoreboard API and sorting policy.

## 7. In-memory storage design

### Active matches

```text
ConcurrentHashMap<Long, MatchState> activeMatches
```

`MatchState` is an internal repository object containing the current immutable `Match` snapshot and a per-match lock. It is not exposed outside the persistence package.

### Active-team index

```text
ConcurrentHashMap<String, Long> activeTeamToMatchId
```

The key is a canonical case-insensitive team name generated using trimmed input and `Locale.ROOT`. This index makes duplicate-team detection direct rather than requiring a scan of all matches.

The display/storage value in `Match` is the normalized capitalized name; the canonical key is used only for uniqueness checks.

### Finished history

```text
LinkedHashMap<Long, Match> finishedHistory
```

The map is insertion-ordered and bounded to 20 entries. Access is protected by a dedicated history lock. Finished matches are inserted in finish order; when the size exceeds 20, the eldest entry is removed.

## 8. Concurrency model

The design avoids one global lock around all operations.

### Starting a match

1. Normalize and validate both team names and scores/identity inputs.
2. Allocate a unique ID/start order using `AtomicLong.incrementAndGet()`.
3. Reserve both canonical team names atomically with `putIfAbsent`.
4. If either reservation fails, remove any reservation made by this attempt and report a duplicate-team error.
5. Insert the active `MatchState` into `activeMatches`.

The reservation sequence must be rolled back if active-match insertion fails. The implementation should use a small repository-level creation lock or an equivalent reservation object to prevent an observable partial reservation and to make the two-team reservation operation atomic as a unit. This lock is used for creation coordination only; score updates and summary reads do not take it.

### Updating a score

The repository obtains the `MatchState` from `activeMatches`, then synchronizes on that state's lock:

1. Read the current immutable snapshot.
2. Reject the operation if the state is already finished or absent.
3. Validate non-negative scores.
4. Replace the snapshot with a new immutable `Match`.

Different matches can be updated concurrently. Updates to one match are serialized.

### Finishing a match

The repository synchronizes on the match state's lock, marks the current snapshot as finished, removes the team reservations, removes the state from active storage, and adds the final snapshot to history while holding the history lock.

An update racing with finish is serialized by the same per-match lock. Exactly one operation observes the active state first; the other receives an unknown/invalid-operation error according to the resulting state.

The active-to-history move is performed as one repository operation. A `getMatch` call may observe either the active or finished representation during a concurrent finish, but it must not observe a mutable or partially constructed match.

### Summary reads

The repository copies each active state's current immutable snapshot. No returned object shares mutable state with the repository. The service then sorts the copied matches. Concurrent updates can result in a mixed-time summary, which is the documented consistency guarantee.

### Lookup

`findAny` checks active storage and then the bounded history. Both sources contain immutable match snapshots, so lookup is safe without exposing internal mutable state.

## 9. Error handling

Use one runtime exception type:

```java
public final class ScoreboardException extends RuntimeException {
  private final ErrorCode errorCode;
}
```

Initial error codes:

```text
INVALID_TEAM_NAME
SAME_TEAM
DUPLICATE_ACTIVE_TEAM
INVALID_SCORE
MATCH_NOT_FOUND
MATCH_ALREADY_FINISHED
INVALID_MATCH_OPERATION
```

Only codes required by an implemented validation or state transition should be used. The public exception message should be concise and should not be used as a machine-readable contract.

## 10. Testing strategy

### Unit tests

- match construction and immutability;
- team normalization and case-insensitive comparison;
- same-team rejection;
- non-negative score validation;
- unique ID/start-order generation;
- summary ordering by total score and most-recent start order;
- update replacement semantics, including score reduction;
- finishing and lookup behavior;
- unknown, finished, duplicate-team, and invalid-score errors;
- history limit and oldest-entry eviction.

### Functional tests

Use `ScoreboardService` with `InMemoryMatchRepository` and verify complete flows:

- start several matches, update them, and compare the required summary order;
- finish a match and verify it leaves the summary;
- retrieve active and recently finished matches through `getMatch`;
- verify a finished match disappears from lookup after history eviction.

### Concurrency tests

- start matches concurrently with overlapping teams and verify no team is active in two matches;
- update different matches concurrently;
- update one match concurrently and verify every final snapshot has a valid non-negative score pair;
- race update against finish using `CyclicBarrier` or `CountDownLatch`;
- read summaries concurrently with updates and verify each returned match is internally consistent;
- finish more than 20 matches concurrently and verify history never exposes more than 20 retained matches.

Tests should coordinate threads with synchronization primitives rather than arbitrary sleeps and should assert observable behavior rather than the concrete map or locking implementation.

## 11. Alternatives considered

### Separate ID and start-order counters

This makes the two concepts independent, but adds state and creates an unnecessary possibility for disagreement. Reusing the monotonically increasing ID is simpler and deterministic for this library.

### Timestamp-only ordering

Timestamps represent real start time but may be equal or have insufficient precision for deterministic ordering. They are retained as domain data but are not used for tie-breaking.

### One global lock

A single lock would simplify correctness but would serialize unrelated score updates and summary reads. Per-match locking plus narrowly scoped repository/history coordination provides better concurrency with modest complexity.

### Mutable public matches

Mutable objects would reduce allocations but allow clients to observe changes after a method returns and would make thread-safety harder to reason about. Immutable snapshots provide a clearer API contract at small cost.

### Copy-on-write active map values without per-match state

Replacing immutable values in a `ConcurrentHashMap` is simple for score updates, but coordinating update-versus-finish and moving a match to history becomes harder. An internal per-match state gives one synchronization point for that lifecycle.

## 12. Implementation sequence

1. Create the Maven project and package structure.
2. Implement normalization, `Match`, error codes, and exception type.
3. Implement `MatchRepository` and in-memory active/history storage.
4. Implement the four required scoreboard operations.
5. Add unit, functional, and concurrency tests.
6. Add README and AI usage documentation.
7. Introduce `getMatch` in a distinct Git commit after the required functionality is complete.
